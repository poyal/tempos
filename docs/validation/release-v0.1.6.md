# Tempos v0.1.6 업데이트 검증

배포 후보의 소스는 `d07c6be49dabc15edcd9703a43396438871e889b`입니다. Release 실행 파일의 SHA-256은 `8070B62C908A0879EDD36FD06360A22A810F7B62740939AD174DAD4A64127904`입니다. 무설치 ZIP에서 읽은 실행 파일과 대조했고, 전용 패치 ZIP 안의 327개 파일을 설치 패키징 목록과 크기·해시별로 대조했습니다. 두 배포 경로는 같은 제거 프로그램을 사용합니다.

| 검사 | 범위 | 통과 | 실패 | SKIP |
| --- | --- | ---: | ---: | ---: |
| Release 핵심 | 파서·서명·해시·저장 등 | 9,705 | 0 | 0 |
| ASan 핵심 | 같은 검사, 주소 검사기 적용 | 9,705 | 0 | 0 |
| Release `--updates` | 실제 Windows 창·저장·프로세스·파일 교체, HTTP 목업 | 118 | 0 | 0 |
| ASan `--updates` | 같은 시나리오, 주소 검사기 적용 | 118 | 0 | 0 |
| 센서 패키징 검사 | 로컬 센서 요청·파이프 테스트 | 22 | 0 | 0 |

Release E2E 실행 폴더는 `test-results/e2e-20261124-213202-710 업데이트 검사`, ASan은 `test-results/e2e-20261124-213121-430 업데이트 검사`입니다. 실행별 TestHost 설치 폴더에서 0.1.6과 99.0.0 시험 실행 파일 사이의 교체를 검사했습니다. 서명이 틀린 패치, 다운로드 취소, 일반 재시작 후 적용, 사용자 파일 충돌, 삭제할 파일의 잠금, 새 앱의 초기 종료, 강제 중단 후 복구, 정상 기동 확인과 결과 표시를 확인했습니다. 기존 사용자 설치의 설정·백업·자동 시작 값도 실행 전후에 대조했습니다.

첫 핵심 검사는 기본 샌드박스의 DPAPI 저장에서 실패해 같은 실행 파일을 사용자 세션에서 재검사했습니다. 초기 ASan 복구 검사는 재시작 PID를 받지 못했습니다. 시험에서 중단된 도우미의 종료를 기다린 뒤에도 실패가 재현되었으며, 복구 요청 프로세스의 PID·생성 시각과 실제 종료까지 확인하도록 수정한 뒤 위 결과를 얻었습니다. 설치 패키징 첫 시도는 제거 프로그램 생성기의 종료 코드 때문에 중단되었고, 생성 성공 코드를 명시한 뒤 패키징했습니다.

개발 PC에는 사용자 설치가 있어 실제 설치·제거는 SKIP했습니다. 날씨·달력·OAuth·위치 서비스 실연동은 수행하지 않았습니다. 배포 후 공개 다운로드 검증은 일반 E2E와 별도로 기록합니다.

## 깨끗한 Windows 설치 검사

Windows Server 2022 GitHub 호스팅 러너에서 공개 v0.1.5 EXE를 설치하고 v0.1.6 EXE로 전환한 뒤 관리 파일의 해시를 검사했습니다. 첫 지원 버전의 ZIP 경로를 검사하기 위해 같은 공개 키와 새 프로토콜을 갖춘 0.1.5 시험 실행 파일을 준비했습니다. 서명된 최종 0.1.6 ZIP을 작업 폴더에 미리 받아 둔 상태에서 앱 내 적용을 실행해 기동 확인, Windows 설치 버전 등록, 사용자 파일·시계 설정 보존, 실제 제거 프로그램과 바로가기 정리를 확인했습니다. [성공한 Windows 실행](https://github.com/poyal/tempos/actions/runs/45396016891)

첫 원격 실행은 GitHub 초안 조회 권한 때문에 다운로드 단계에서 중단됐습니다. 두 번째 실행은 실제 설치 파일 대조 후 PowerShell에서 창 제목을 빈 문자열로 전달해 설정 창을 찾지 못했습니다. 검증 도구에 Win32 NULL 포인터를 전달하도록 고쳤고, 최종 검사는 동일한 태그·서명·배포 파일로 통과했습니다. [초안 조회 실패 기록](https://github.com/poyal/tempos/actions/runs/45394841703) · [창 조회 실패 기록](https://github.com/poyal/tempos/actions/runs/45395199635)
