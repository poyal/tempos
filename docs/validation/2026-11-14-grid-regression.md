# 격자·편집 수명주기 회귀 검증

작성일: 2026-11-14. 계획한 검사 실행을 마쳤다. 기능·스트레스·ASan·실제 2시간 혼합 검사는 통과했으며, 단독 30분 성능의 CPU 시간 목표는 미달이다. 따라서 전체 성능 기준까지 통과했다고 표현하지 않는다. 실행별 원본은 `test-results`, 집계와 원본 경로는 [기계 판독 결과](2026-11-14-grid-results.json)에 보존한다.

## 수정한 동작

- 실제 스냅과 격자 표시를 8 DIP로 통일했다. 이번 작업 중의 4 DIP 표시보다 간격을 두 배로 넓혔다. 각 선의 픽셀 좌표를 개별 변환해 DPI 반올림 오차가 누적되지 않는다.
- 모든 크기·배율의 너비와 높이를 완전한 8 DIP 칸 수로 맞췄다. Slim 150% 높이는 112 DIP, XL 150% 높이는 1,264 DIP다. 렌더러도 늘어난 창 크기에 맞춰 배경을 채운다. 위젯 사이 16 DIP 여백은 유지한다.
- 화면 경계 밖이나 충돌 지점에 놓으면 같은 모니터에서 가장 가까운 빈 격자를 찾는다. 거리 동률은 Y, X 순으로 결정한다. 공간이 없으면 기존 위치를 유지한다.
- 기존 4 DIP 레이아웃을 가져오거나 화면 경계가 달라져도 연결된 모니터 안에서 원래 위치에 가깝게 복구한다. 임시 배치를 원본 저장 좌표에 덮어쓰지 않는다.
- 설정창을 닫으면 편집을 끝내고 격자를 제거한다. 창 재구성 시 진행 중인 드래그와 해당 창의 마우스 캡처를 정리한다.
- 같은 위치에 놓는 동작은 설정 파일을 다시 쓰지 않는다. 드래그가 아직 적용하지 않은 설정 입력을 지우지 않는다.
- DirectWrite 텍스트 레이아웃을 최대 256개, 모델명 글자 크기 계산을 최대 128개로 제한해 재사용한다. 위치 탐색은 장애물 경계 후보를 사용해 반복 픽셀 탐색을 줄였다.
- 배경과 CPU/GPU/메모리의 고정 제목·아이콘·모델명은 최대 8개·4 MiB 비트맵으로 재사용한다. 크기·DPI·테마·배경 투명도·고대비·모델명·그래프 표시가 키에 포함된다. 큰 표면은 원래 경로로 그리며 사용률·온도·그래프·메모리 수치는 매번 갱신한다. 그래프는 유효 구간별 경로로 묶고 오류 샘플을 가로질러 잇지 않는다.

## 검증 방법

- 고정 시드 2,000개 배치 사례를 독립적인 전체 격자 탐색과 대조한다. 근접 배치·빈자리 선택·멱등성·잘못된 좌표·공간 부족을 검사한다.
- DPI 96/120/144/168/192, 크기 5종, 배율 100/150/200%, 음수 화면 원점·연결 해제·재연결·경계를 계산 모델로 검사한다.
- 실제 Windows UI에서는 9종의 37개 지원 크기 × 3배율을 검사한다. 크기뿐 아니라 왼쪽·오른쪽·위·아래 네 변의 실제 픽셀 경계를 확인하고 Slim 150% 배경의 네 변 픽셀도 검사한다.
- 설정창 닫기·재열기 20회, 편집 전환 12회, 네 변 드롭, 잠금·클릭 통과·캡처 취소·재시작을 확인한다.
- 1개/64개 위젯에서 각각 준비 100회와 측정 1,000회 드래그를 실행한다. 내부 이동·드롭과 프로세스 간 왕복 p95를 별도로 기록한다. TestHost 전용 네이티브 메시지 배치는 실제 입력 처리기를 실행하며 결과 좌표를 주입하지 않는다. 실제 OS SendInput 검사는 별도 `windows-real`이다.

- 성능은 실제 로컬 Windows 수집, 외부 HTTP 목업, 표시된 위젯을 사용한다. 기본 5개 예산은 평균 CPU 0.1%, p95 0.3%, CPU 시간 4 ms/초, private 32 MiB, working set 48 MiB다.
- 지속 검사는 실제 2시간 동안 추가·설정·드래그·닫기·숨김·삭제와 프로세스 재시작을 반복한다. 잠금·절전·비정상적인 실행 중단은 통과 시간으로 세지 않는다.

기능·컨트롤별 연결은 [기능 검증 추적표](feature-matrix.md), 재실행 명령은 [E2E 실행 지침](../e2e.md)에 있다.

## 실패 이력과 판정 보정

2343… 리비전의 5분 준비·1분 측정은 CPU 시간 11.31 ms/초로 실패했다(기준 4). 평균 CPU 0.0943%, p95 0.2586%, private 18,518,016 bytes, working set 44,097,536 bytes였으며 이 실패는 보존한다. 스레드별 진단 후 정적 배경·고정 요소 재사용과 그래프 호출 묶음을 추가했다. 60초 준비·약 60초 스레드 진단의 6.39→5.06→4.53 ms/초 수치는 원인 분석용이며 정식 성능 통과로 집계하지 않는다.

초기 실패 원본은 삭제하거나 최종 통과로 바꾸지 않았다. 구형 Slim 150% 충돌·오른쪽 경계 복원이 멀리 이동하던 문제는 먼저 실패하는 단위 검사로 재현한 뒤 수정했다. 합성 드래그 사이에 실제 포인터 메시지가 끼어드는 자동화 경쟁은 소유 HWND 검증을 포함한 네이티브 배치로 분리했고 실제 SendInput은 별도로 검사했다.

별도 계측 복사본에서 부분 그리기를 실험했다. 화면 픽셀 일치는 통과했지만 충분한 성능 이득을 입증하지 못해 제품 코드에 반영하지 않았다. 진단용 복사본의 헤더 의존성 인코딩 문제로 발생한 초기 실행 실패도 보존했다. 진단이 겹친 `performance-optimized-five-30min-20261114-052652`는 취소 상태이며 정식 30분 결과로 사용하지 않는다. 그 실행기만 중단하고 소유 TestHost를 정상 종료했으며 설치본·설정 보존을 확인했다.

스트레스 초기 실패에서 추가 핸들의 스레드 시작 주소는 Windows 런타임 모듈에 있었으며 앱 창은 늘지 않았다. 매 조작의 UIA 조회가 자동화 RPC 작업자 풀을 함께 자극하고, 첫 15분 갱신이 준비 구간 밖에 있었다. 준비 갱신과 네이티브 컨트롤 핸들 재사용을 추가하고 자원 읽기 시점을 UI 스레드로 옮겼다. 허용 누수 기준은 늘리지 않았다. 진단 실행의 핸들 종류·스레드 모듈·숨은 창 목록을 보존한다.

최종 바이너리의 첫 스트레스는 마지막 한 표본의 핸들 +2로 실패했다. 전후 구간 모두 363~365개였으며 추가 스레드는 `ntdll.dll`에서 시작했다. 다음 실행에서는 중앙값 361→361, 최대값 365→363인데 최솟값 359→361만 증가했다. 앱 스레드 핸들은 9→9였고 변동은 Windows 유휴 작업자에 있었다. 따라서 동일한 5분 구간의 중앙·최대 자원 수와 앱 스레드 수를 판정하며, 유휴 작업자 종료 정책에 좌우되는 최소값은 진단용으로 구분한다. 원래 끝점 값도 `endpoint`에 남긴다. 이전 실패를 소급해서 통과 처리하지 않고 새 방법으로 재실행한다.

## 실행 경계와 SKIP

- 외부 API는 모두 HTTP 응답 경계 목업이다. Open-Meteo·기상청·Google Calendar·OAuth·현재 위치의 실제 서버 성공을 주장하지 않는다. 등록되지 않은 요청이나 실제 서버 대체 요청은 실패다.
