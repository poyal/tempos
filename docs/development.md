## 실측에 따른 설계 조정

기본 렌더링은 **공유 Direct2D DC 렌더 타깃 + 창별 32비트 DIB + UpdateLayeredWindow**다. 글꼴과 브러시를 공유하고 변경 시에만 그린다. DirectComposition 구현도 코드에 남아 있으나 기본 경로는 아니다. 브라우저, GPU 프레임 루프, 강제 Working Set 축소를 사용하지 않는다.

초기 1분 비교에서 DirectComposition 경로의 최대 Private Bytes 약 65.4 MiB, Working Set 약 61.6 MiB가 저주기 DC 경로에서는 약 18.2 / 39.6 MiB였다. 이 수치는 짧은 기술 비교 결과이며 최종 성능 인수 결과로 사용하지 않는다.

Windows 11 빌드 26300와 Wallpaper Engine 환경에서 wallpaper WorkerW 또는 Progman의 직속 자식은 실제 화면에 가려졌다. **SHELLDLL_DefView 안의 아이콘 목록 위**에 위젯 창을 연결하는 경로로 수정했고 실제 위치 검사와 레이어를 포함한 화면 캡처로 표시를 확인했다. Explorer 내부 창 계층에 의존하므로 다른 Windows 업데이트·바탕화면 확장 도구에도 동일하게 동작한다고 보장하지 않는다. 실제 바탕화면 아이콘 위치를 자동 이동시키지는 않는다.

하나의 바탕화면 부모 아래에서는 Windows가 자식에게 같은 창 DPI를 줄 수 있다. 위젯의 렌더링·좌표·히트 테스트는 대상 모니터의 DPI를 별도로 사용하여 서로 다른 모니터 배율을 맞춘다.

GPU PDH 인스턴스의 LUID가 대문자 16진수로 반환되어 DXGI 키와 일치하지 않던 오류를 수정했다. 대소문자를 정규화하고 프로세스별 값을 같은 엔진으로 모으며, 합계 카운터를 중복 계산하지 않는다. 실제 NVIDIA GeForce RTX 4070 Ti에서 UIA 요약에 사용량이 표시되는 것을 확인했다.

반복 생성·제거 시험에서 기존 힙의 5초 후 Private Bytes 증가가 2,793,472바이트로 기준을 넘었다. Windows 11의 [Segment Heap](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests#heaptype)을 매니페스트로 선택한 뒤 동일한 짧은 시험에서는 1,081,344바이트로 줄었다. 이 비교만으로 누수 원인을 단정하지 않는다. 최종 반복 시험은 별도로 5분 준비·1,000회 생성/제거·5분 안정화 조건을 사용한다. Working Set 강제 비우기나 테스트 직전 힙 정리 호출은 사용하지 않는다.

## 검증 환경과 증거

- Windows 11 x64, 빌드 26300, 논리 프로세서 16개.
- 주 모니터 3840 × 2160, 150%; 보조 모니터 1920 × 1080, 125%. 보조 모니터 원점 `(1902,2160)`.
- VS 2022 Build Tools 17.14 / MSVC 14.44 / SDK 10.0.26100.0 / CMake 3.31 / Ninja.
- .NET SDK 10.0.401 / FlaUI.UIA3 5.0.0. 테스트 사용자 세션에서 DPAPI와 UI 자동화를 실행했다.
- 원본 실행 기록은 `test-results/e2e-*/results.json`, `stress.json`, `performance-*/report.json`, `samples.jsonl`과 `artifacts/*tests.log`다. 화면 캡처에는 사용자의 바탕화면이 포함될 수 있어 Git에 넣지 않는다.

한글 MSVC의 `/showIncludes`가 잘못 해석되어 헤더 의존성 0개로 빌드되던 문제를 발견했다. `scripts/build.ps1`에서 콘솔 UTF-8과 새 CMake 구성을 사용하고 전체 재빌드했다. Ninja가 실제 헤더 의존성을 기록하는 것을 확인한 뒤 E2E를 다시 실행했다. 수정 전 실패 로그를 성공 기록으로 합산하지 않는다.

앱과 TestHost가 같은 지역표를 동시에 복사하던 빌드 경쟁도 공유 `tempos_data` 대상으로 제거했다. 매니페스트 변경은 명시적 링크 의존성으로 추적한다. UI 캡처는 투명 레이어를 포함하는 `CAPTUREBLT`를 사용하며, 각 E2E 실행 폴더에 분리 저장한다.

이 자동화 세션에서는 FlaUI `SendInput` 및 `SetCursorPos` 호출 후 실제 커서가 이동하지 않았고 `Shell.ToggleDesktop`도 관찰 가능한 창 상태 변화를 만들지 않았다. 따라서 이전의 단축키 호출 자체를 Win+D 성공 증거로 사용하지 않는다. 최종 시각 검사는 이 항목을 명시적으로 SKIP 처리한다. 드래그는 실제 소유 위젯 창에 Win32 마우스 메시지를 보내 저장 좌표·4 DIP 정렬·잠금·클릭 통과를 확인한다. 앱은 전역 커서의 뒤늦은 위치 대신 각 메시지의 좌표를 사용하고, 드래그 중 DPI 알림이 기존 위치로 되돌리지 않도록 처리했다. 물리 마우스와 실제 Win+D 검증은 남아 있다.

CPU는 논리 프로세서 16개로 정규화했으며 모든 표본 간격은 약 1초다. 실제 날씨 키와 Google 계정은 없는 상태다. 9종에서는 실제 네트워크·디스크·시스템 수집과 로컬 달력을 사용했다. 따라서 정상 외부 API까지 포함하는 전체 성능 인수 결과가 아니다.

30분 기준 측정과 반복 자원 측정은 드래그 이벤트 좌표 보완 전 빌드에서 수행했다. 수집·예약·렌더링·자원 소유 구현은 동일하지만, 최종 실행 파일과 SHA-256은 다르므로 최종 파일의 짧은 측정을 별도로 기록했다. 짧은 측정을 30분 또는 24시간 검증으로 대체하지 않는다.

최종 파일의 30초 예열·3분 측정은 원시 CPU 4ms/초 목표를 초과했다. 이 결과도 유지하고 5분 예열 조건으로 추가 확인했다. 추가 측정은 평균 CPU 0.0108%, 원시 CPU 1.73ms/초로 해당 목표 이내였지만, 부하와 예열 조건에 따른 편차를 보인 만큼 모든 상황에서 목표를 충족한다고 해석하지 않는다. 반복 시험의 통과와 30분 메모리 증가는 장기 누수 없음의 증명이 아니다.

## 아직 검증하지 않은 범위

- 기상청 실제 개인 키를 통한 서버 응답과 Google 실제 계정의 브라우저 승인·토큰 갱신. 사용자가 클라이언트 ID를 아직 준비하지 않았으므로 설정 입력 경로와 모의 응답 검증까지 구현했다.
- 24시간 후 메모리 증가량·추세. 반복 생성/제거와 짧은 측정의 통과를 ‘누수 없음’의 증명으로 사용하지 않는다.
- 실제 Explorer 프로세스 종료·재시작, 물리 모니터 분리/재연결, 실제 시스템 절전·로그온 잠금. 창 재등록 메시지와 배치 로직의 모의 검증은 이 항목의 대체 증거가 아니다.
- Windows 10, ARM64, 다른 Windows 11 빌드, 64개 초과 논리 프로세서, 모든 GPU/외장 디스크 조합, 4K 200% XL 최악 조건.
- 정상 기상청 요청·실제 Google 일정까지 포함한 성능 인수 조건과 DWM·공유/전용 GPU 메모리의 앱 미실행 대비 비교. 여기의 프로세스 CPU·메모리 수치를 시스템 전체 비용으로 해석하지 않는다.

설계에서 확장 여지를 남긴 화면 가림 감지, GPU 장치 제거 후 전체 렌더 장치 재생성, 날짜 격자의 개별 UIA 자식 탐색, API별 세밀한 오류 진단·일일 사용량 추정, 여러 다른 달력 조회 기간을 통합하는 캐시는 이번 구현에 모두 포함되지 않았다. 현재 구현은 날짜 상세의 읽기 전용 접근과 위젯 전체 요약 UIA를 제공한다. 외부 연동이 특정 캘린더에서 실패하면 완전했던 이전 조회 스냅샷을 유지한다.
